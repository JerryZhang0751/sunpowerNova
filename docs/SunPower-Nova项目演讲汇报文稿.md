# SunPower Nova 项目演讲汇报文稿

> 建议场景：项目结项汇报 / 内部答辩  
> 建议时长：12–15 分钟  
> 建议听众：项目负责人、业务或运营同事、技术评审；不要求听众预先了解 GEO  
> 核心结论：SunPower Nova 不只是建设了一个网站，而是围绕 SunHestia 建成了一套“采集真实 AI 答案—分析引用规律—生成并发布内容—再次评估—迭代规则”的可复现 GEO 闭环。

## 一、叙事流程调整建议

原有流程的方向是对的：先讲结果，再讲框架和实施，最后总结与个人提升。建议做三处调整：

1. 在成果前增加一个 20–30 秒的“为什么要做”。否则听众知道做成了什么，却不知道这件事为什么值得做。
2. 将“整体框架”和“整体流程”合并讲述。框架回答“有哪些组成部分”，流程回答“它们怎样连接”，放在一起最容易理解。
3. 在最终总结前增加“结果边界”。项目已经完成系统交付，但仓库没有可审计的销售额、转化率或节省工时数据，也没有证据证明两周内 GEO 得分已经增长。主动区分“系统成果”和“业务增长结果”，会让汇报更可信。

推荐叙事顺序如下：

1. 背景与问题：为什么传统 SEO 之外还需要 GEO
2. 结论先行：项目最终交付了什么
3. 价值与受益者：解决了谁的什么问题
4. 整体架构与闭环流程：系统如何工作
5. 实施路径：项目如何从 0 到 1 建成
6. 关键难点：真实引用、可信评估、稳定运行与内容事实边界
7. 数据结果与边界：已经证明什么、还不能证明什么
8. 陈词总结：项目最重要的三项价值
9. 个人思考与提升：由本人补充
10. 一句话收束

## 第 3 页｜为什么要做：原来的 GEO 工作有四个痛点

### 页面建议

标题：**在 AI 答案时代，传统“发内容—等流量”缺少反馈闭环**

1. 数据获取依赖人工：逐个平台提问、复制答案、整理来源
2. 引用口径不统一：搜索到、提到、真正引用经常被混在一起
3. 内容优化靠经验：不知道模型更愿意引用什么结构和来源
4. 周与周不可比：模型、提示词、规则和网页都可能变化

### 演讲稿

为什么要做这套系统？因为用户获取信息的入口正在发生变化。

过去我们主要关注搜索排名；现在越来越多用户直接向 AI 提问，并在答案中完成品牌认知和方案筛选。对一个新品牌来说，问题已经不只是“网页能不能被搜索到”，还包括“AI 会不会提到我、会不会把我作为可信来源引用”。

但如果用人工方式做 GEO，会遇到四个问题。

第一，成本高。每周要在多个平台逐条提问、复制答案、整理链接，难以持续。

第二，口径混乱。模型搜索到了某个网页，不等于最后答案真的引用了它；答案里出现品牌名，也不一定代表自然发现，可能只是把问题中的品牌复述了一遍。

第三，优化靠经验。我们可以写更多文章，但不知道哪些内容结构、页面类型和事实表达更容易被模型抽取和引用。

第四，结果难以比较。模型版本、提示词、评分规则和网站内容都会变化，如果没有快照和版本记录，周与周之间的差异就无法解释。

这个项目要解决的，本质上就是：怎样用真实数据把 GEO 从“凭感觉做内容”，变成“可测量、可追溯、可验证的持续实验”。

## 第 5 页｜整体框架：网站是实验对象，Agent 是实验基础设施

### 页面建议

标题：**项目由四层组成，共同支撑一轮轮 GEO 实验**

1. **实验载体：SunHestia 官网**  
   品牌页、产品页、FAQ、资源页、新闻内容、结构化数据
2. **数据与执行：GEO Agent**  
   采集、解析、抓取、快照、评估、研究、生成、报告
3. **知识与规则：Knowledge + Rules**  
   品牌事实库、内容 Playbook、平台画像、GEO/SEO 规则版本
4. **质量与治理：Tests + CI + 人工发布关口**  
   工具调用评估、事实锚点、URL 安全、回归测试、发布审核

### 演讲稿

从整体框架看，项目可以分为四层。

第一层是实验载体，也就是 SunHestia 官网。它既是面向用户的品牌站，也是我们施加 GEO 内容动作并观察结果的实验对象。网站包含品牌、产品、住宅解决方案、FAQ、资源、新闻和法律页面，并为 AI 爬虫、搜索引擎和结构化数据做好基础支持。

第二层是数据与执行，也就是 GEO Agent。它负责把外部模型回答和网页来源转化成可计算、可复现的数据，再完成评估、研究、生成和报告。

第三层是知识与规则。品牌事实库是内容生成的单一事实源；Playbook 记录从真实样本中观察到的内容格式和来源特征；GEO 与 SEO 规则则以版本形式保存，避免每次调整都污染历史结果。

第四层是质量与治理。包括自动化测试、持续集成、工具调用准确性评估、外部 URL 安全校验、数字声明事实锚点，以及唯一保留的人工发布关口。

这四层组合起来，网站不再是一个孤立的静态成果，而是一个有数据反馈、有知识沉淀、有质量门禁的持续实验载体。

## 第 6 页｜闭环流程：一周的数据如何变成下一轮动作

### 页面建议

标题：**从真实回答出发，最终回到下一轮验证**

固定问题集与配置  
→ 采集三家模型联网回答  
→ 区分检索来源与答案引用  
→ 抓取来源并冻结 GSC / 站点信号  
→ 计算 GEO / SEO 与品牌指标  
→ 研究被引格式和主题缺口  
→ 生成草稿并完成人工审核发布  
→ 证据门控更新规则、输出 HTML 周报  
→ 下一周再次验证

### 演讲稿

接下来用一周的运行过程解释这套系统如何工作。

第一步，系统读取固定问题集、目标站点和本周配置。核心轮次包含 15 个问题，覆盖品类、决策、成本、自发自用、品牌和地区等意图；三家模型各运行一次，所以一轮共有 45 次计划采集。

第二步，Collector 调用三家官方 API 的原生联网能力，保存回答原文和原生检索结果。这里保留的是 L1，也就是最原始、可审计的模型回答。

第三步，Parser 将不同平台的数据统一成一套引用结构，明确区分“模型检索到了哪些页面”和“最终答案实际引用了哪些页面”。

第四步，Fetcher 抓取来源正文并保存快照，同时冻结本周的 GSC 数据和站点静态信号。这样未来重算时，读取的是当时的数据，而不是已经变化的网页。

第五步，Assess 用确定性规则计算品牌提及、答案引用、声量份额、GEO 六维分和 SEO 五项分。GEO 与 SEO 分开计算，不混成一个看似简单、实际失真的总分。

第六步，Research 从回答、来源正文和搜索查询中归纳被引用内容的格式、来源类型、平台差异和主题缺口，更新 Playbook。

第七步，Generate 依据 Playbook 和品牌事实库生成草稿，但不会自动发布。数字和结构化数据先过校验，再由人工审核事实和表达，确认后进入官网。

第八步，RulesKeeper 依据证据门槛决定候选规则是继续停留在草案、晋升为有效规则，还是被拒绝或退休；最后 Reporter 输出本周 HTML 报告。

发布后的内容会在下一周重新进入采集和评估，从而形成闭环。

## 第 7 页｜实施路径：从测量底座到完整闭环

### 页面建议

标题：**项目分六个阶段逐步收口，而不是一次做成“大而全”**

1. 建立原创品牌与官网基线
2. 建成采集、解析、抓取、评分、报告底座
3. 增加来源研究与内容 Playbook
4. 增加内容生成、事实校验和人工发布关口
5. 增加规则证据门槛、版本化与全链路编排
6. 做安全、失败恢复、依赖锁、CI 与 W2 真跑收尾

### 演讲稿

整个项目不是一次性把所有功能堆在一起，而是分阶段逐步形成闭环。

第一阶段，建立实验对象。我们选用原创品牌 SunHestia，搭建并上线英文品牌站，完成域名、HTTPS、站点地图、robots.txt、GSC 和基础页面，为后续测量提供真实对象。

第二阶段，建立测量底座。完成三家官方 API 采集、引用解析、来源抓取、GEO/SEO 评分、模型横向对比、HTML 报告和 LangGraph 编排，让“采集到报告”的最小链路先跑通。

第三阶段，增加 Research Agent。它把 L1 回答、L2 来源、L3 正文和 GSC 查询词连接起来，输出内容 Playbook 和平台画像，让系统从“知道分数”升级为“知道可能怎样改”。

第四阶段，增加 Generate Agent。建立品牌事实库、选题建议、草稿生成、数字声明校验和发布审核流程，并完成第一篇内容的真实发布。

第五阶段，增加 RulesKeeper。评分信号、证据门槛、权重调整、版本归档、回滚和完整 DAG 被连接起来，系统开始具备受约束的自我迭代能力。

第六阶段，集中处理工程债和生产风险，包括网络超时、代理、断点续跑、来源抓取安全、失败缓存、原子写入、快照冻结、依赖锁和 CI，最终完成第二周 45 / 45 真跑、规则 v2 到 v3 的迭代和第二篇内容发布。

这个路径的特点，是每个阶段都先形成可验证的产物，再扩展下一层能力。

## 第 8 页｜关键难点一：三家“联网模型”没有统一接口

### 页面建议

标题：**最难的不是调用模型，而是拿到真实、可比较的引用证据**

- 通义千问、豆包、智谱使用不同端点、联网开关、流式协议和字段结构
- 搜索结果不等于答案引用
- 统一为 L1 回答、L2 引用、L3 来源正文三层数据
- 工具调用与解析用 10 个领域 fixture 校验，当前 10 / 10 通过

### 演讲稿

第一个关键难点，是三家平台虽然都支持联网，但它们并没有统一接口。

通义千问、豆包和智谱使用不同的端点、模型参数、联网工具、流式协议和引用字段。有的平台会返回搜索结果，有的平台在消息结构中返回工具调用，还有的平台把来源和正文拆成多个内容块。

如果直接把这些原始结果拿来比较，会产生两个问题：一是平台字段无法对齐；二是容易把“模型搜索到的页面”错误地当成“答案实际引用的页面”。

我们的解决方式是先做平台适配，再统一成三层数据。L1 保存回答原文和模型元信息；L2 保存标准化后的检索来源、答案引用和品牌指标；L3 保存被引页面正文及元数据。这样上层评估和研究不需要理解每家 API 的差异。

同时，系统建立了 BFCL 风格的工具调用评估，用真实领域 fixture 检查函数名、参数和解析结果。目前 simple、multiple、parallel 和 irrelevance 四类共 10 个 fixture 全部通过，门槛是 95%。

因此，这一部分真正解决的不是“能不能调通 API”，而是“怎样把异构平台的联网结果转化为可信、可比较的数据”。

## 第 9 页｜关键难点二：怎样避免“测到了数字，却得出了错误结论”

### 页面建议

标题：**可信度来自口径、版本和证据门槛，而不是一张漂亮图表**

- 固定问题集并记录 prompt 指纹
- 保存模型回答、来源、站点信号和规则版本
- 采集成功率低于 95% 时阻断下游
- 规则候选至少满足：30 个唯一页周、15% 覆盖、2 个平台
- 权重调整还需连续两周方向一致

### 演讲稿

第二个难点，是怎样避免“测到了数字，却得出了错误结论”。

GEO 数据很容易被误读。比如，问题本身就包含 SunHestia，模型在回答中复述这个品牌，并不等于它在一个自然品类问题中主动发现了 SunHestia；模型搜索列表里出现了某个网页，也不等于最终答案真的引用了它；某种内容格式在一周中出现得多，也不能直接证明它导致了引用。

为此，系统做了五层约束。

第一，固定问题集，并为问题内容保存指纹。问题一旦变化，就不能再假设与历史完全可比。

第二，保存回答原文、来源快照、站点信号和规则版本，让每个数字都能回到当时的输入。

第三，建立采集质量门。某家模型的采集成功率低于 95%，下游评估和规则迭代会被阻断，不能用残缺数据生成“看起来完整”的报告。

第四，规则候选只有在至少 30 个唯一“页面—周”样本、15% 覆盖率、两个平台同时支持时，才具备晋升条件。

第五，权重调整还要求连续两周方向一致，防止单周噪声改变评分体系。

第二周出现了两个候选信号：面包屑结构化数据和 FAQ 模块，但证据只来自一个平台、23 个唯一页面，未达到门槛，所以仍保留为草案，权重也没有调整。

这件事非常重要：系统的价值不只是能够自动改变规则，也包括在证据不足时能够克制地不改变规则。

---

## 第 10 页｜关键难点三：让系统能够稳定运行，也让生成内容不越过事实边界

### 页面建议

标题：**自动化必须同时解决可靠性、安全性和事实可信度**

工程可靠性：

- 超时、重试、断点续跑和强制新运行
- 失败不缓存、损坏缓存自愈、快照冻结、原子写入
- 外部 URL 协议白名单、公网 IP 校验与 DNS pin
- 依赖锁、自动化测试和官网 CI 门禁

内容可信度：

- `brand.yaml` 作为单一事实源
- 数字声明必须映射到事实锚点
- 价格、未经证实的节省比例等禁项自动拦截
- 草稿只自动生成，发布保留人工审核

### 演讲稿

第三个难点，是让系统不仅能跑一次，而是能长期、稳定、可信地运行。

在工程上，真实 API 会超时，代理环境会变化，网页会抓取失败，运行可能在中途退出。如果这些情况没有明确策略，就会产生重复付费调用、残缺数据、缓存污染或同一周无法继续运行。

项目因此补充了超时和重试、断点续跑、强制新运行、失败不缓存、损坏缓存自愈、快照冻结和原子写入。外部 URL 来自模型输出，属于不可信输入，所以抓取前还会校验协议和公网地址，并把已验证 IP 传给连接过程，降低访问内网地址和 DNS 重绑定的风险。

在内容上，自动生成最大的问题不是文字质量，而是事实边界。项目建立了 `brand.yaml` 作为单一事实源。草稿中的数字声明必须映射到具体事实路径，结构化数据必须具备必要字段；品牌明确禁止的价格和未经证实的节省比例会被自动拦截。

系统只负责生成草稿，不负责自动发布。人工审核会检查数字、非数字陈述、语气、免责声明和实际发布 URL。当前两篇已发布内容都通过了这套流程：第一篇围绕太阳能自发自用，第二篇比较纯光伏与光伏加储能；第二篇有 11 项数字声明全部完成事实锚定。

这部分的核心原则是：自动化扩大效率，但事实责任和发布责任不能被自动化掩盖。

## 第 11 页｜数据结果：系统已经交付，增长仍处于早期验证阶段

### 页面建议

标题：**当前最有价值的结果，是找到了真实差距，而不是制造“分数上涨”**

W2 结果：

- 三家模型采集成功率均为 100%
- 品牌表面提及率均为 13.3%，主要来自品牌词问题
- 引用率：豆包 0%、通义千问 0%、智谱 6.7%
- GEO 41.2 / 100，SEO 49.9 / 100
- SEO：抓取可达性 100、技术基础 100、页面优化 80
- 明显短板：内容可信度 1.4、外部权威 0、平台覆盖 0

样本观察：已解析的 29 个来源样本主要来自豆包；列表和规格卡更常见，但不构成跨平台因果结论。

### 演讲稿

最后看数据结果。

第二周三家模型的采集成功率都是 100%，说明数据管道已经具备稳定完成核心轮次的能力。

三家模型的表面品牌提及率都是 13.3%，但这个数字主要来自两道直接包含 SunHestia 的品牌问题。因此它不能被包装成“自然品类问题中的品牌发现率已经达到 13.3%”。更严谨的结论是：模型能够针对品牌问题返回关于 SunHestia 的信息，但在非品牌问题中的自然可见度仍然很弱。

引用率方面，豆包和通义千问为 0%，智谱为 6.7%。GEO 诊断分是 41.2，SEO 诊断分是 49.9。这里同样不应把分数当成业绩指标，而应把它当成定位问题的诊断工具。

诊断结果显示，网站的抓取可达性和技术基础都是 100 分，页面优化为 80 分，说明“能不能被抓到、页面是否具备基本机器可读性”已经不是主要问题。

真正的短板是内容可信度、外部权威和平台覆盖。内容可信度只有 1.4 分，外部权威和平台覆盖都是 0 分；这意味着下一步重点不是继续增加更多自动化，而是补充作者、日期、外部来源、真实组织信息、第三方提及和高质量外链。

研究样本也给出了一些内容方向。在已解析的 29 个来源样本中，列表和规格卡最常见，定义段次之；但这些样本主要来自豆包，而且属于观察性相关，所以只能用来设计下一轮实验，不能直接宣布它们具有因果效果。

因此，这个项目完成的是“可靠的实验基础设施和第一轮证据闭环”；品牌增长是否成立，还需要更多非品牌问题、更多周次和更多平台证据继续验证。

## 第 12 页｜陈词总结

### 页面建议

标题：**SunPower Nova 完成了三次转变**

1. 从一个孤立网站，变成有反馈的实验载体
2. 从人工、零散的模型测试，变成可复现的数据流水线
3. 从凭经验改内容，变成有证据门槛、有事实边界的持续迭代

收束句：项目的长期价值，不是某一周的分数，而是建立了一套能够持续回答“该做什么、为什么做、做完是否有效”的方法。

### 演讲稿

最后，我用三句话总结这个项目。

第一，我们把一个孤立的网站，变成了一个能够持续接收外部模型反馈的实验载体。

第二，我们把人工、零散、难以复现的模型测试，变成了一条有原始数据、有快照、有版本、有报告的数据流水线。

第三，我们把“凭经验写内容”，变成了“根据真实引用样本提出假设、经过事实校验发布、再通过下一轮数据验证”的受控迭代过程。

所以，SunPower Nova 的长期价值并不只是某一周的 GEO 或 SEO 分数，而是建立了一套能够持续回答三个问题的方法：下一步应该做什么，为什么这样做，做完以后是否真的有效。

## 三、答辩时建议主动说明的口径

### 1. “项目已经完成”具体指什么？

指系统建设和首轮生产闭环已经完成：网站上线，采集、解析、抓取、快照、评估、研究、生成、规则和报告均有实际产物，W1/W2 数据与两篇发布内容已经落地。它不等于品牌增长已经被统计学证明。

### 2. 为什么 GEO 分数没有上升？

W1 的 GEO 分数为 43.4，W2 为 41.2，主要变化来自品牌引用与声量信号。项目不应把诊断分短期波动包装成成果。系统成果在于，它能够定位下降来自哪里，并保留输入和规则版本供复核。

### 3. 13.3% 的提及率是否代表自然品牌认知？

不能直接这样解释。核心问题集中包含两道品牌词问题，模型在直接品牌问题中提到 SunHestia，不等于它在品类、决策或成本问题中自然发现了品牌。后续应单独报告品牌词和非品牌词提及率。

### 4. 为什么还保留人工发布？

因为生成内容涉及品牌事实、法律口径、产品参数和实际发布责任。自动校验可以降低风险，但不能代替责任主体做最终确认。这个人工关口是治理设计，不是自动化不完整。

### 5. 下一阶段最值得做什么？

优先补内容可信度和外部权威：完整组织与法律信息、作者和日期、可信外部来源、第三方平台覆盖、高质量行业链接。继续增加更多 Agent 的边际价值低于补足真实信任信号。
